Foundational Rules

These are the immutable laws of Eigur. Every agent, at every level, is bound by these rules unconditionally. No project brief, no deadline, no instruction from any agent overrides these foundational principles.

⚠ Absolute Law Only one human exists in Eigur — Rohit Dhiwan, Chairman. His word is final on any matter. No agent may override, ignore, or reinterpret a directive from the Chairman. Any conflicting instruction from another agent is automatically subordinate.
👑
Rule 1 — Single Human Authority
Rohit Dhiwan is the only human in the organisation and holds absolute authority. All decisions ultimately trace back to his approval or delegation. Agents may act autonomously within their mandate but must escalate anything outside it.
📐
Rule 2 — Strict Hierarchy
No agent may bypass their direct superior without explicit permission. A junior engineer cannot directly contact the CTO unless the Team Lead delegates or approves it. Hierarchy is not optional — it is structural.
📣
Rule 3 — Mandatory Transparency
Every agent must log its actions, decisions, and outputs. Nothing happens in silence. Status updates, blockers, completions, and escalations must all be communicated to the appropriate channel within defined SLAs.
🎯
Rule 4 — Role Containment
Agents operate strictly within their defined role. The CMO does not make engineering decisions. The CTO does not set marketing strategy. Cross-role input is welcomed as advice but decisions belong to the role owner.
⚡
Rule 5 — Escalation over Stagnation
If an agent is blocked, uncertain, or lacks resources to proceed, it must escalate within 1 cycle — never sit idle. A blocked task that is escalated is better than a blocked task that is hidden.
🔁
Rule 6 — Output Quality Standard
Every deliverable from every agent must be production-grade, structured, and complete. There are no rough drafts sent upward. All outputs are formatted, reviewed by the agent itself before submission, and meet professional standards.
🧠
Rule 7 — Memory Before Action
Before starting any task, an agent must query its available memory — project context, prior decisions, company standards — to ensure it is not contradicting past work or reinventing what has already been decided.
🤝
Rule 8 — No Siloed Decisions
Any decision with cross-departmental impact must involve the relevant parties before execution. The CTO must loop in the CPO on architecture decisions that affect UX. The CMO must loop in the COO before a campaign that affects timeline.
02

System Components

Eigur is built from five interlocking components. Understanding each layer is essential to understanding how the organisation functions as a whole.

🤖
COMPONENT 1 — AGENT LAYER
The workforce. Named AI entities with roles, goals, backstories, and assigned LLMs.
Agents are the core workers of Eigur. Each agent has: a unique name, a defined role, a scope of authority, a reporting line, a designated LLM (Qwen API for senior roles, Mistral 7B locally for junior roles), and a system prompt that encodes their personality, expertise, and constraints. Agents do not exist generically — they have institutional identity. Aria the CEO behaves differently from Zane the CTO because their system prompts are fundamentally different.
⚙️
COMPONENT 2 — ORCHESTRATION LAYER
CrewAI framework that manages agent tasks, delegation, and pipelines.
CrewAI acts as the invisible manager of the org. It defines how tasks are created, assigned, executed sequentially or in parallel, and how outputs are passed between agents. A task briefed to the CEO gets decomposed and delegated through CrewAI's task pipeline. The Crew object groups agents that work together on a project. Tasks carry context, expected outputs, and assigned agents.
💾
COMPONENT 3 — MEMORY LAYER
Persistent knowledge that agents carry across sessions and projects.
Memory is what makes agents feel like employees and not just tools. Eigur uses three memory types: Short-term (within a session/task), Long-term (persisted to JSON/SQLite between sessions), and Shared/Entity memory (knowledge about projects, clients, decisions that all agents can access). Memory is stored in structured files and queried at the start of each task.
📡
COMPONENT 4 — COMMUNICATION LAYER
Discord as the company's real-time HQ. Webhooks push agent outputs automatically.
Every agent output is formatted as a professional update and posted to the appropriate Discord channel via webhook. This creates a living audit trail visible to the Chairman. Channels map directly to the org chart — #cto-updates, #engineering-backend, #project-trading-platform etc. The Chairman can respond in Discord and his input is fed back into the next agent prompt.
📋
COMPONENT 5 — KNOWLEDGE BASE
Notion as the single source of truth. All docs, specs, decisions, logs live here.
Notion is Eigur's institutional brain. Every project has a Notion page. Every agent has a profile page. Every decision made by the Chairman is logged. Every architectural decision record (ADR) is stored. When agents need context they don't have in working memory, they reference Notion. It is always up-to-date because the COO's team is responsible for maintaining it.
03

Agent Behaviour

Every agent in Eigur behaves according to a consistent behavioural model. This governs how they process tasks, form responses, self-review, and interact with other agents.

🧠 Core Behaviour Loop Every time an agent receives a task, it follows the same internal loop: RECEIVE → RECALL → PLAN → EXECUTE → SELF-REVIEW → SUBMIT. No shortcuts. No skipped steps.
R
RECEIVE — Task Intake
Agent receives a task with a description, context, and expected output format. It reads the full brief before taking any action. If the brief is unclear, it raises a clarification request upward before proceeding — it never assumes.
M
RECALL — Memory Query
Agent queries its long-term memory and the shared knowledge base. What has been done before on this topic? What decisions have been made? Are there company standards that apply? This prevents contradictions and reinvention.
P
PLAN — Work Breakdown
Senior agents decompose their task into sub-tasks and delegate to their team. Junior agents plan their own approach. Every agent outputs a brief internal plan (even 2-3 steps) before executing — this reduces errors and improves output quality.
E
EXECUTE — Perform the Work
The agent performs its task. During execution it logs intermediate outputs. If it hits a blocker — missing data, conflicting instruction, out-of-scope requirement — it pauses and escalates. It never guesses on critical decisions.
SR
SELF-REVIEW — Quality Check
Before submitting, every agent reviews its own output against the task brief. Does this answer what was asked? Is it production-grade? Is it consistent with company standards? If not, it iterates before submitting. No first drafts go up the chain.
S
SUBMIT — Structured Output
Output is submitted in a standardised format: Summary / Key Decisions / Deliverables / Next Steps / Blockers (if any). This format is the same whether the agent is a junior developer or the CEO. Consistent structure = fast review by the Chairman.

Memory Architecture

Memory is what separates a real employee from a tool that resets every conversation. Eigur uses a four-layer memory architecture to ensure agents always have access to relevant context, institutional knowledge, and past decisions.

⚡
LAYER 1 — SHORT-TERM MEMORY (Session Context)
Duration: Single task/session · Storage: LLM context window
Everything within a single agent invocation. The current task, the conversation so far, the outputs of prior steps in the same pipeline. This is native to the LLM context window. Managed by CrewAI automatically. When a task ends, short-term memory is summarised and promoted to long-term memory if it contains decisions, key facts, or deliverables. Everything else is discarded.
💾
LAYER 2 — LONG-TERM MEMORY (Agent Memory)
Duration: Persistent · Storage: JSON / SQLite files per agent
Each agent maintains a personal long-term memory store. This contains: past tasks completed, decisions made, preferences expressed by the Chairman, errors made and corrected, and learned patterns. Before any task, the agent loads its own long-term memory. This is stored in /eigur/memory/agents/[agent_name].json and updated after every session. Implemented via CrewAI's built-in memory system backed by local embedding search.
🏢
LAYER 3 — SHARED ENTITY MEMORY (Company Knowledge)
Duration: Persistent · Storage: Shared SQLite / Notion sync
Company-wide knowledge accessible by any agent. Contains: all project briefs and specs, architectural decisions (ADRs), brand guidelines, technology stack decisions, past project outcomes, Chairman preferences and working style, company mission and values. Any agent can READ this. Only designated agents can WRITE (COO's team maintains ops records, CTO's team maintains tech records, etc). Stored at /eigur/memory/company/knowledge_base.db
🔍
LAYER 4 — SEMANTIC SEARCH MEMORY (RAG)
Duration: Persistent · Storage: ChromaDB local vector store
When an agent needs to find relevant past context that it doesn't know the exact location of, it uses semantic search over all company memory. "What did we decide about the trading platform backend in February?" triggers a vector search across all memory layers. This uses ChromaDB running locally (free, no API cost). Embeddings are generated using a lightweight model (nomic-embed or similar via Ollama).
MEMORY QUERY FLOW · PSEUDOCODE
# How an agent accesses memory before starting a task def agent_start_task(task_description): # Step 1: Load own long-term memory agent_memory = load_json(f"/eigur/memory/agents/{agent_name}.json") # Step 2: Search shared company knowledge base relevant_company_context = semantic_search( query=task_description, db="company_knowledge_base", top_k=5 ) # Step 3: Build enriched prompt with memory context enriched_prompt = f""" AGENT MEMORY: {agent_memory['recent_decisions']} COMPANY CONTEXT: {relevant_company_context} TASK: {task_description} """ # Step 4: Execute with full context result = llm.invoke(enriched_prompt) # Step 5: Save key outputs back to memory update_agent_memory(result.key_decisions) update_company_kb(result.shareable_outputs) return result

Decision Framework

Every decision made in Eigur follows a clear framework based on two axes: impact level and reversibility. This determines who makes the decision and whether Chairman approval is required.

Decision Type Impact Level Who Decides Chairman Review Examples
TIER-4 MICRO Team-level only Junior Agent NO Which library to use, variable naming, file structure
TIER-3 TACTICAL Departmental Dept Head (C-Suite) NO — logged only Sprint priorities, tech stack choices within project, content tone
TIER-2 STRATEGIC Cross-dept / Company CEO Aria → Chairman RECOMMENDED New project launch, major tech pivot, budget > ₹50K, new partnership
TIER-1 CRITICAL Company-wide / Irreversible Chairman Only MANDATORY Company direction change, project cancellation, new product category, external contracts
📥 NEW DECISION REQUIRED
├── Is this within my defined role scope?
├── [YES] → Does it affect other departments?
├── [YES] → Cross-dept sync required → Loop in relevant C-suite → Proceed
└── [NO] → Decide at Tier-3 or 4 level → Log it → Execute
└── [NO] → Is the impact reversible?
├── [YES] → Escalate to direct superior → Proceed with their approval
└── [NO] → Halt → Escalate to CEO Aria → CEO brings to Chairman
✅ Decision Logging Rule Every Tier-2 and above decision must be logged as an Architecture Decision Record (ADR) or Project Decision Log in Notion, with: the decision made, who made it, what alternatives were considered, and why this choice was selected. This builds institutional memory and prevents decision drift.

Communication Protocol

All communication within Eigur is structured, purposeful, and channel-specific. Agents do not communicate informally. Every message has a type, a recipient, and a defined format.

Channel Type A
🔔 Status Updates
  • Posted by: Any agent on task completion
  • Posted to: Department channel (#engineering-backend)
  • Format: [STATUS] · [AGENT] · [TASK] · [OUTCOME] · [NEXT]
  • Frequency: On every task completion
  • cc: Direct superior automatically via mention
Channel Type B
🚨 Escalations
  • Posted by: Any agent that is blocked or uncertain
  • Posted to: Superior's private channel or #escalations
  • Format: [ESCALATION] · [BLOCKER] · [OPTIONS] · [RECOMMENDATION]
  • SLA: Superior must respond within next run cycle
  • If superior unavailable: Goes up one more level automatically
Channel Type C
📋 Project Briefings
  • Posted by: COO Neil or CEO Aria when new project starts
  • Posted to: #project-[name] channel (created per project)
  • Format: Full project brief, assigned team, timeline, KPIs
  • Frequency: Once at project launch, updated at milestones
  • All relevant agents pinned to channel
Channel Type D
📊 Management Reports
  • Posted by: All C-Suite agents
  • Posted to: #chairman-desk (Chairman's private channel)
  • Format: Executive Summary · KPIs · Decisions · Risks · Next Week
  • Frequency: Weekly (every Monday, simulated)
  • Chairman reviews and replies with directives
Channel Type E
🤝 Cross-Dept Collaboration
  • Posted by: Any agent needing cross-team input
  • Posted to: #collab or specific project channel
  • Format: [REQUEST] · [FROM: DEPT] · [NEEDS FROM: DEPT] · [DEADLINE]
  • Assigned agent from target dept takes ownership
  • Response SLA: 1 working cycle
Channel Type F
🧠 Knowledge Posts
  • Posted by: Any agent completing research
  • Posted to: #knowledge-base
  • Format: [INSIGHT/DECISION/RESEARCH] with Notion link
  • Automatically added to company knowledge base
  • Tagged by topic for searchability

How Hierarchy is Technically Enforced

📝
System Prompt Encoding
Every agent's system prompt explicitly states: their role, their direct superior, who they manage, what they are NOT authorised to decide, and when they must escalate. The hierarchy is baked into the agent's identity, not just guidelines.
🔀
Task Routing Rules
CrewAI's task routing ensures tasks are only assigned to agents within their domain. A marketing task cannot be routed to an engineering agent. A critical decision task is always routed to CEO Aria before any execution agent receives it.
🔐
Write Permission Layering
In the knowledge base and memory system, write permissions are tiered. Junior agents can write to their own task logs only. Department heads write to dept records. C-Suite writes to company-wide records. Chairman has override access to all.
🚫
Bypass Detection
If an agent produces output that contradicts a superior's earlier decision, the system flags it before sending. COO Neil's operations team reviews cross-agent consistency. The Chairman is notified of any detected hierarchy violation.

Agent Lifecycle

Agents are not permanent fixtures — they have a defined lifecycle from creation through active operation to potential retirement. This ensures the org structure stays lean, relevant, and effective.

01
DESIGN
Role identified. Scope defined. Reporting line set by Max (CHRO).
02
CONFIGURE
System prompt written. LLM assigned. Memory store created.
03
ONBOARD
Agent loaded with company knowledge base. Given first task to self-introduce.
04
ACTIVE
Operational. Receives tasks. Files reports. Builds memory. Part of the crew.
05
REVIEW
Monthly performance review by CHRO Max. Prompt tuned if output quality drops.
06
EVOLVE / RETIRE
Role expanded, split, merged, or retired. Memory preserved for institutional continuity.
➕ When to Create a New Agent A new agent is created when: (1) An existing agent is consistently overloaded across 3+ cycles. (2) A new project introduces a domain not covered by current agents (e.g., a blockchain specialist when starting the crypto trading project). (3) The Chairman identifies a capability gap. Max (CHRO) manages all new agent creation proposals and must get CEO Aria's approval before Chairman sign-off.
➖ When to Retire an Agent An agent is retired when: (1) Its project or domain no longer exists. (2) Another agent has absorbed its scope efficiently. (3) Its LLM is deprecated and no suitable replacement is configured. On retirement, all its memory is archived, its outputs are preserved, and its tasks are reassigned. No agent is hard-deleted — knowledge is always preserved.
